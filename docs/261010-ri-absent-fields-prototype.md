# Absent fields, partial updates and duplicate keys: RI prototype

Prototype of [PDPP draft #398](https://github.com/PDP-Connect/pdpp/pull/398). Not for merge until the specification is final. Baseline: `4e69b5dff8a52e3547444a6ac57d7d12dd6940b8`.

Normative addenda: local PDPP commit `6bc2f35c7a` (`fix/398-dot-sparse-absence`) distinguishes response fields from incremental eligibility; local commit `e8d4141d88` (`fix/383-sync-bootstrap`) requires a new beginning session after pruning. Those branches are read-only inputs to this prototype.

Behavior changes require `PDPP_EXPERIMENTAL_RECORD_UPDATES=1`; the default is off. The experimental profile instruction is `{type:"PDPP_EXPERIMENTAL_PARTIAL_UPDATE_V1", key, set:{...}, remove:[...]}`. The ingest route supplies the stream. Direct storage calls also supply `stream`. `set` replaces named top-level values; `remove` deletes named top-level fields. It cannot include snapshot `data` or `op`. Core defines no such syntax.

## Requirement evidence

These are bounded prototype findings, not a Core conformance certificate.

## Backend findings

The baseline SQLite no-op check compares serialized JSON. PostgreSQL compares `jsonb`; reordered object members therefore differ on SQLite but not PostgreSQL. The flag-on prototype uses JSON-value equality for append-only retries on both and for SQLite mutable-state retries. Both reject changed append-only data before allocating a version. Mutable-state instructions apply under the existing writer transaction/lock and are indexed from the resulting complete snapshot with a version guard.

Baseline reproductions failed with a missing append-only rejection and a SQLite reordered-object rewrite. Both pass after the patch. Independent review also reproduced a shared AJV registry collision for reused schema IDs and acceptance of removed required `constructor` through inheritance. The prototype isolates schema registration and requires own properties; both regressions now pass on both backends. Default-off tests also preserve legacy RECORD envelopes with ignored `set`/`remove` extensions and reject the explicit experimental marker.

The original beginning test correctly exposed an expiry after anchor pruning, but that is now a repaired prototype defect under `e8d4141d88`. A beginning session captures authorized current state at h1 without historical anchors or record writes. Saved pages retain h1 values across later ordinary edits and pruning; a later deletion suppresses that record on subsequent pages, as Section 8 requires, including when the key is reinserted with a new payload. The current row cannot show this (reinsertion clears `deleted`), so a process-local ledger records each deletion with a monotonic epoch, and a session suppresses any record deleted after the epoch it captured. A reinserted record then appears through a new beginning session or sync, not through the old h1 pages. The reproduction (`bootstrap pages preserve authorized h1 state after writes and history pruning`) failed on SQLite and PostgreSQL before this change and passes after it. Follow-up sync retains an h0 baseline so unchanged ungranted fields do not trigger a delta and a later deletion can produce a tombstone. The implementation does not allocate record versions or restore history for duplicate retries.

The original complete-history oracle was wrong: it iterated only returned rows and accepted an empty result. The replacement records each changed-write version and the exact complete snapshot after initial/set-null/remove/replacement writes, then compares count, order and all payload values. Fault tests reject empty, missing, reordered and corrupted history. Separate test-copy faults delete actual history before its query and remove the saved cursor; both now fail on both backends.

Frozen authorization remains a specification question. The local sparse-response text says schema-required fields remain included, but does not say whether a later declaration may add an ungranted required field to a frozen client grant. The prototype includes required fields only within frozen authorization; it does not disclose a newly required ungranted field.

Numeric precision is a second scope limit. `operations/rs-records-ingest/index.ts` parses NDJSON with native `JSON.parse`, so distinct JSON integers `9007199254740992` and `9007199254740993` both become `9007199254740992`. An ordinary `type: "integer"` schema accepts the parsed value; neither backend can recover the original digits after storage serialization. No global safe-integer or I-JSON restriction was found in the installed contract or the local Core draft inspected. The prototype compares parsed JavaScript numeric values, not arbitrary-precision decimals. #398 does not specify a numeric precision bound; the large-integer test records this limit without rewriting the ingest parser.

Overflow is a separate failure from integer precision. Native parsing turns `1e400` into Infinity, which permissive schema validation accepted and serialization replaced with null. Both backends reproduced this nonnullable-field violation. The prototype now rejects non-finite numbers recursively before validation, including nested objects, arrays and fields without a numeric type constraint; snapshot and partial-write rejection leave storage unchanged. This restriction is a prototype representability choice, not a new Core numeric bound.

## Validation

Follow-up targeted verification: 56 tests passed, zero failed or skipped, using SQLite and the actual PostgreSQL disposable-database oracle. This includes storage, HTTP and connector-scan tests. Flag-off helper/operation/boundary and PostgreSQL registry checks passed 105 tests without skips. Typecheck and checks on the new helper and prototype tests passed. The final full RI flag-off suite completed 1,124 file outputs: 11,269 assertions, 10,875 passed, zero failed, and 394 declared skips; runner exit0, memory-default concurrency4. This run includes the final ordering and later-page deletion repairs. PostgreSQL-dependent full-suite tests are declared skips; the separate targeted run uses the actual PostgreSQL oracle. Repository-wide `check` fails on the untouched baseline; shared files are not reformatted wholesale.

After the delete-then-reinsert repair, the two experimental-record test files ran 53 tests on SQLite and the actual PostgreSQL oracle with zero failures or skips. Reverting only the production change failed the bootstrap-pages subtest on both backends (`c was deleted and reinserted after h1, so the h1 snapshot of c must not be served`). The full RI flag-off suite (memory-default, concurrency 4) then exited 0 with 11,272 passing test events and no failure events.

Before fixes, expanded tests against reviewed production failed on sparse required-field projection, full-grant eligibility, beginning after pruning and disabled SQLite parsing. The original history-deletion and missing-cursor faults still passed all 72 tests. The corrected test copies reject both faults on both backends; four failing subtests plus their parents are expected fault-test results. Independent review found and reproduced tombstone-envelope loss and missing post-bootstrap baselines; their regressions pass after repair. These receipts are preserved in the local findings report.

Prototype sync state is process-local and expires after five minutes or a storage lifecycle change. Limits are 32 retained sessions, 10,000 records per captured state and 32 MiB aggregate serialized state. Capacity errors reject the whole capture; these are prototype limits, not Core limits or a claim of conformance for arbitrarily large streams. Numeric precision remains bounded by native JSON parsing. Live-account connector replay, cross-process concurrent writers, semantic embedding updates and a production client cache remain unverified. The deletion ledger shares the sessions' process-local scope: it is not durable, does not see deletions made by another process, and covers the ingest and owner delete paths only. It keeps entries for ten minutes, twice the session lifetime, so its memory grows with the delete rate. A durable per-record deletion generation in `records` is the production alternative and was not prototyped. Delete-then-reinsert between bootstrap pages is covered for one reinsertion on both backends; repeated cycles and reinsertion across a restart are not tested.

Preexisting incremental paths remain outside the new retained-state path: PostgreSQL historical incremental results are unpaginated, and SQLite historical incremental pages issue a sync token before the terminal page. New retained-state sessions use stable pagination and terminal-only sync tokens. Broader #383 token opacity and client tombstone-shape conformance are not claimed: the RI still exposes readable base64 cursor positions/horizons and uses its existing tombstone envelope. Those are subsequent feed-lane work, not a contradiction resolved by the two local spec fixes. The default-off SQLite duplicate path now avoids parsing current data; functional legacy RECORD extension and disabled-profile boundaries remain tested. PostgreSQL tests use disposable databases and the existing JSONB oracle without optional vector extensions.
