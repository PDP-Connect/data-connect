## 2. Version allocation, gaps, reuse, and commit ordering

| Path:line | What it does | Change row? | Risk |
|---|---|---|---|
| `server/queries/records/ingest/allocate-next-version.sql:1-38`; called in `server/records.ts:2374-2384, 6436-6446` | SQLite uses one `INSERT ... ON CONFLICT DO UPDATE ... RETURNING`, assigning `MAX(counter, MAX(record_changes.version), MAX(records.version)) + 1`; its write transaction is `BEGIN IMMEDIATE` (`records.ts:1670-1679, 6363-6375`). | Caller writes row in same transaction. | SQLite writers serialize. | `server/postgres-records.ts:1610-1682, 1981-2120` | Postgres uses `GREATEST(1, history max+1, records max+1)` initially, then on conflict `GREATEST(counter, history max, records max)+1`; upsert row locking serializes concurrent allocators. Ingest runs within transaction-scoped connector-instance write fencing and appends current row plus history before commit. | Yes, same transaction. | Competing writes for an instance serialize on the fence/counter row. A later version cannot commit first and then be followed by a lower one for that stream. Rollbacks may make attempted numbers unobservable; they do not leave durable gaps. History pruning does not lower the floor while current records remain. |
| `server/postgres-records.ts:3035-3134`; `server/records.ts:6623-6628` | Reset deletes counter and both record tables. | No. | Version reuse after reset is possible. The separate `record_reset_generation` checkpoint changes (`postgres-records.ts:3060-3095`; `records.ts:6566-6597`) help internal snapshot readers but do not emit a copy-worker event. |

Assessment: for an uninterrupted stream, committed append versions are ordered and safe for a last-version cursor if the reader polls committed rows by ascending version. There is no normal commit-later-with-lower-version race in these paths. Reset is the exception: a consumer retaining only numeric last-version can skip reused versions unless it also tracks reset generation/lifecycle. Pruning can remove unread events; see Q4.

## Verdict (5 lines)

1. Ingest upserts and explicit per-record deletes atomically append ordered `record_changes` rows in both backends.
2. In-place derived-column repairs, blob state, bulk deletes, reset and connection/manifest erasure are not represented as ordinary change rows.
3. Version allocation is serialized and monotonic per uninterrupted stream; reset can reuse numbers, and consumers must track reset/lifecycle state.
4. History pruning can erase unread events, so a log-only mirror needs a bounded-lag guarantee and source reconciliation.
5. Original textual connection IDs, keys, versions and timestamps can be imported; preserve uniqueness and reset Postgres `records.id` sequence after explicit ID import.
