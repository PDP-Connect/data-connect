# Approve a server-hosted request-URI consent page

## Sub-features

This feature is the complete user flow below. The source map's steps, branches, exact visible copy, product forms, and repo-relative code references are retained here.

## How to get to it (user POV)

### 5. Approve a server-hosted request-URI consent page

**Who starts:** An outside OAuth/device client. **Where:** Reference server `GET /consent?request_uri=…` (or `approval_id`); device-flow authorization may first show `/device?user_code=…`. This is HTML generated by the reference server, not the Next console. Its shared stylesheet is served at `/__pdpp/hosted-ui.css`; header identifies the instance and footer says “Secured by PDPP.” **Code:** `reference-implementation/server/routes/as-consent.ts:700-733,736-801`; `reference-implementation/server/routes/as-consent-ui-helpers.ts:1320-1345,2451-2584,2614-2711`; `reference-implementation/test/hosted-ui.test.ts:141-159,174-188` (V).

1. The owner opens the verification URL supplied by the client. This branch is used when OAuth arrives with `authorization_details` or `connector_id`; without those, the server sends the owner to the console challenge page in Flow 6. The server checks owner session and pending request. If an owner session is configured, the person may need to sign in; the browser returns to the same request. **V** `reference-implementation/server/routes/as-authorize.ts:1534-1632`; `reference-implementation/server/routes/as-consent.ts:700-729`; owner auth middleware set in `:15-19`.
2. The page title/eyebrow is “Data access request”; lede: “Review what this app is asking for. Your server will only release what you allow here.” Heading: “<app name> wants access to your data”. It can show a verification code, client identity, client-authored display, client claims, manifest-described “Requested streams”, protocol facts, and a warning for ongoing access. **V** `reference-implementation/server/routes/as-consent-ui-helpers.ts:2474-2583`.
3. Single-source requests show the requested streams and access mode. Ongoing requests warn: “Continuous access” and “This is long-lived access with no explicit expiry. The client may keep reading until you revoke the grant.” (If retention is present, the alternative mentions the retention bound.) The owner sees `Access mode`, source/connector, retention where supplied, stated purpose, and requested stream names. These values come from the request; this page has no source, field, date-range, access-mode, or grant-expiry controls. The owner can allow the request as presented or deny it. **V** `reference-implementation/server/routes/as-consent-ui-helpers.ts:2483-2542`.
4. If review is not finalized, `Allow access` submits the review first; a required AI-training request additionally requires the checkbox “I explicitly agree to AI training use”. The owner then sees a second “Final approval” page titled “Approve the reviewed data access”; it lists reviewed client/subject, source declaration, purpose, exact reviewed streams, AI-training choice, and expiry, with `Allow access` and `Deny`. If already-reviewed material exists, this final confirmation is the immediate page. **V** `reference-implementation/server/routes/as-consent-ui-helpers.ts:2325-2444`.
5. Batch requests say “Review each source. Your server will only issue grants for sources you confirm.” and “<app> wants access to several sources”. Cards show requested streams, source, access mode, sensitivity, and client-stated purpose. Each source starts selected. `Narrow this source (optional)` says “Uncheck streams or fields to share less, or tighten a start date. You can only reduce what was requested; you cannot add anything here.” Its staged streams and fields start checked; any requested start date is prefilled. The owner can check “I confirm allowing all N sources: <source list>” and choose `Allow all sources`, or use source checkboxes and `Confirm selected sources`, or `Deny`. Risk summary labels are `Sources in this request`, `Sensitive sources`, `Continuous-access sources`, `Sources with no time bound`, `Sources without field projection`, and `Total streams`. Broad or unsafe requests can suppress `Allow all sources` and require per-source confirmation; the warning names the reason. The next page says “Final approval” / “Approve the reviewed sources”, restates approved source order and exact reviewed streams, then requires “I confirm this reviewed decision” before `Approve reviewed decision`; `Deny` remains available. The expiry is shown as a reviewed value; no expiry picker appears here. After approval the page says “Access approved” / “Grant issued” or “Source grants issued”; the server returns a single-use consent exchange code that expires shortly for client redemption. A bearer is not placed in the HTML response. **V** `reference-implementation/server/routes/as-consent-ui-helpers.ts:1926-1942,1996-2042,2051-2119,2122-2317`; `reference-implementation/server/routes/as-consent.ts:162-310`.

**Branches/failures:** Missing `request_uri` and `approval_id`: server error `request_uri or approval_id is required`. Invalid request URI: `request_uri is invalid`. Missing/expired/already-used request renders “This consent request is no longer available” / “Link expired or already used” and says: “This approval link has expired, was already approved or denied, or was created on a different session. Return to the app that asked for access and start the request again to get a fresh link.” Malformed/stale review and invalid selection fail closed with server-owned error text. Denial ends with “Access Denied”. **V** `reference-implementation/server/routes/as-consent.ts:706-717,745-775`; `reference-implementation/server/routes/as-consent-ui-helpers.ts:1326-1345`; result HTML in `reference-implementation/server/routes/as-consent.ts:811,902-919`.

**Denial result copy:** The response uses “Access Denied” as the OAuth/page title. The owner-facing result is headed “You didn't share anything” and says “The app didn't get any of your data. You can close this tab.” **V** `reference-implementation/server/routes/as-consent.ts:902-919`; `reference-implementation/server/routes/as-consent-ui-helpers.ts:3788-3791`.

**Choices and defaults:** For single-source requests, the client has already declared the source, streams, access mode, and (when present) expiry; the owner sees those values and can allow or deny, but cannot narrow them here. For batch requests, the owner can drop sources, streams, or fields and tighten an already requested start date, but cannot widen the request. Defaults preserve the staged selection. If no review artifact exists, `Allow access` first submits the review. For AI training, it stays unavailable until “I explicitly agree to AI training use” is checked. The second page restates the saved expiry under `Grant expiry`. **V** `reference-implementation/server/routes/as-consent-ui-helpers.ts:1996-2042,2325-2362,2375-2444,2474-2572`.

**Afterwards:** Grants appear under `/grants`; the client redeems its exchange code at `POST /consent/exchange`. Server-hosted HTML separates the human decision from protocol details. It can be visually different from the console because the reference server owns and renders the document. **V** `reference-implementation/server/routes/as-consent.ts:162-310`; `apps/console/src/app/(console)/grants/page.tsx:1`.

**Rough edges:** This server-hosted approval page is the request-URI/device-consent path. The no-source MCP OAuth path instead redirects to `/consent?challenge` in the console. `reference-implementation/server/routes/as-consent-ui-helpers.ts:1` also still contains a server-rendered hosted-MCP source picker, but the current `/oauth/authorize` handler does not render it: it redirects to the console challenge at lines 1578-1610. The helper is called when a compatibility `POST /oauth/authorize/mcp-package` request must re-render validation errors (`reference-implementation/server/routes/as-authorize.ts:876-923,1034-1086`); its GET-route comment at lines 1536-1542 still says it shows that picker. Its re-render omits `consent_challenge` even though the POST requires it before approval, so a retry from that compatibility page cannot complete a bound challenge. This makes the server-rendered picker a legacy/recovery surface in this commit, not the normal source-selection page. The request-URI page has `Deny`; the console picker has `Cancel`. **V** `reference-implementation/server/routes/as-consent-ui-helpers.ts:2918-2934,3714-3718`; `reference-implementation/server/routes/as-authorize.ts:1680-1695` and cited files.

## Driving it with Playwright

**Journey status:** `no`; no feature journey is declared. **Result:** `not run`.

**Reachability:** No valid `request_uri` or `approval_id` was created. The flow is not opened by the baseline route list.

**Stops at:** An outside OAuth/device client must create a live pending request. The stack has no such request fixture for capture.

There is no honest feature-flow command for this precondition. The all-route baseline records only route presence when the path is listed; it does not turn a missing consent request, installer, or native desktop state into a feature pass.

## Gotchas

Do not invent a request URI or consent result. Server tests cover the handler but do not produce a user-facing capture.
