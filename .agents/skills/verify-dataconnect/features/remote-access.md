## How to get to it (user POV)

### 4. Make the server reachable from outside the computer (gozar)

**Who starts it:** owner. **Where:** Settings → “Remote access”, `/#remote-access`. **Forms:** desktop managed host and self-hosted server when its reachability host supports the provider. **Evidence:** V for choices, display copy and operation states; provider-specific account steps are partly generated by gozar and appear in `/catalog` / setup-operation responses, so they are dynamic. **Rough edges:** provider catalog descriptions are static but setup actions are generated from gozar; a redesign cannot infer all fields from the row text. The 15-second console-forward timeout and “Details for support” diagnostics are UI-visible without a provider-specific next step. Status can be “Unknown, possibly live” if cleanup is unresolved. Server and desktop catalogs differ by host capabilities and OS support; there is no one static list guaranteed for all installs.

## Driving it with Playwright

**Journey status:** `partly`. **Journey file:** `settings`. **Combined isolated run:** `settings`: **pass**.

**What it verifies:** The capture reaches the remote-access control and its current runtime state.

**Reaches:** Settings shows the Remote access section and the isolated runtime’s “Remote access can’t start on this computer.” message.

**Stops at:** No public tunnel, external DNS, public address, or second device is available offline.

**Run one journey:**

```sh
TEST_SANDBOX_REQUIRE=1 scripts/test-sandbox/test-sandbox --net none --pidns --scratch "$VERIFY_DIR/sandbox-scratch" -- node e2e/harness.mjs capture.spec.ts --output "$VERIFY_DIR/playwright-output" --grep "journey: settings"
```

**Evidence:** `evidence/settings/<run-id>/` contains desktop and phone screenshots plus visible text.

## Gotchas

This is a local loopback harness. It cannot prove access from outside the test namespace.
